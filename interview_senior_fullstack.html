1 How does HashMap work internally? What happens during a hash collision? Hard

Hashing: HashMap stores entries in an array of buckets. When you call put(key, value), it computes key.hashCode(), applies a secondary hash to spread bits, then uses index = hash & (capacity - 1) to find the bucket.

Collision: Two keys landing in the same bucket are stored in a linked list (chain). Since Java 8, if a bucket's chain exceeds 8 nodes and the array has ≥ 64 slots, it converts to a red-black tree (O(log n) instead of O(n)).

Resize: When load factor exceeds 0.75 (default), the array doubles and all entries are rehashed.

// equals() + hashCode() contract — critical!
// Objects that are .equals() MUST return the same hashCode()
// Violating this breaks HashMap/HashSet behavior
Follow-up: "What's the worst-case complexity of get() in a HashMap?" — O(n) with many collisions on the same bucket (pre-Java-8 or bad hashCode). O(log n) after tree conversion. O(1) average.
2 What is the difference between synchronized, volatile, and AtomicInteger? Hard

volatile — guarantees visibility: all threads see the latest write. Does NOT guarantee atomicity. Use for a single flag/state read by multiple threads.

synchronized — guarantees visibility + atomicity + mutual exclusion. One thread at a time. Heavier than volatile; involves monitor lock.

AtomicInteger — uses CPU-level Compare-And-Swap (CAS) instructions. Lock-free, faster than synchronized for single variable updates.

volatile boolean running = true;    // safe flag
AtomicInteger counter = new AtomicInteger(0);
counter.incrementAndGet();           // atomic, no lock

synchronized (this) { // needed for compound actions
  if (map.containsKey(k)) map.put(k, map.get(k) + 1);
}
Rule: use volatile for single reads/writes, Atomic* for single-variable arithmetic, synchronized for compound operations or when guarding multiple variables together.
3 Explain Java's memory model: heap, stack, GC, and memory leaks. Medium

Stack — per-thread. Stores primitives and object references (not objects themselves). LIFO, fast, limited. Freed automatically when method returns.

Heap — shared across threads. All objects live here. Managed by the Garbage Collector. Divided into Young Gen (Eden + Survivor) and Old Gen.

GC basics: Minor GC collects Young Gen (fast, frequent). Major/Full GC collects Old Gen (slower). G1GC (default in Java 9+) divides heap into equal-size regions for predictable pause times.

Memory leaks in Java happen when objects are still referenced but logically unused: static collections that grow forever, listeners never removed, unclosed streams/connections, ThreadLocal not cleared.

A common senior question: "Java has GC, can you still have memory leaks?" — Yes. GC only collects unreachable objects. A reachable-but-unused reference is a leak.
4 What is the difference between CompletableFuture and Future? Medium

Future (Java 5) — blocking. get() blocks the calling thread until the result is ready. Cannot be composed or chained. No built-in exception handling.

CompletableFuture (Java 8) — non-blocking. Supports chaining (thenApply, thenCompose), combining (allOf, anyOf), and exception handling (exceptionally, handle).

CompletableFuture
  .supplyAsync(() -> fetchUser(id))          // async
  .thenApply(user -> enrich(user))            // transform
  .thenCompose(user -> fetchOrders(user.id))  // flatMap
  .exceptionally(ex -> fallback());          // recover
5 Explain SOLID principles with practical examples. Medium

S — Single Responsibility: A class should have one reason to change. Don't mix business logic with persistence or HTTP concerns.

O — Open/Closed: Open for extension, closed for modification. Add new payment methods via a new class implementing PaymentStrategy, not by modifying existing code.

L — Liskov Substitution: A subclass must be usable wherever its parent is used without breaking behaviour. Square extends Rectangle violates this because setWidth() changes height too.

I — Interface Segregation: Don't force clients to implement methods they don't need. Split a fat Worker interface into Workable and Feedable.

D — Dependency Inversion: Depend on abstractions, not concretions. Inject UserRepository (interface), not MySQLUserRepository (class).

Senior interviewers will ask for examples of violations you've seen in production code, not just definitions. Have a story ready.
6 When would you use a Stream vs a for-loop? What are lazy evaluation and short-circuiting? Medium

Streams are ideal for declarative data transformation pipelines (filter → map → collect). They support parallel processing via parallelStream(). For-loops are better when you need early exit with complex logic, index access, or mutating external state.

Lazy evaluation: Intermediate operations (filter, map) are not executed until a terminal operation (collect, findFirst) is called. No unnecessary work is done.

Short-circuiting: findFirst(), anyMatch(), limit() stop processing as soon as the result is determined — even on infinite streams.

Stream.iterate(1, n -> n + 1)  // infinite stream
  .filter(n -> n % 2 == 0)
  .limit(5)                  // short-circuit — stops at 5
  .collect(Collectors.toList()); // → [2, 4, 6, 8, 10]

8 Why is String immutable in Java? What is the String pool? Medium

Immutability — once created, a String's value never changes. Benefits: thread-safe without synchronization; safe as HashMap key (hashCode never changes); security (class names passed to ClassLoader can't be tampered with).

String pool — the JVM maintains a pool of string literals. When you write "hello", the JVM checks the pool; if it exists, the same reference is reused — saving memory.

String a = "hello";              // from pool
String b = "hello";              // same pool reference
String c = new String("hello");  // new heap object, bypasses pool
System.out.println(a == b);      // true  — same reference
System.out.println(a == c);      // false — different reference
System.out.println(a.equals(c)); // true  — same value
c = c.intern();                  // add to pool, return pool ref
Never compare Strings with == — always use .equals(). == compares references, not values. This is one of the most common Java interview traps.
9 Explain Java generics: wildcards (?, extends, super) and type erasure. Hard

Generics — parameterize types at compile time, eliminating unsafe casts and enabling type-safe collections.

PECS rule — Producer Extends, Consumer Super:

// Upper bound — read from it (produces T)
void printAll(List<? extends Number> list) { /* can read, not add */ }

// Lower bound — write to it (consumes T)
void addNumbers(List<? super Integer> list) { list.add(42); }

// Unbounded — only Object methods available
void printSize(List<?> list) { System.out.println(list.size()); }

// Real example from java.util.Collections
public static <T> void copy(List<? super T> dest, List<? extends T> src) {}

Type erasure — generic type information is removed at compile time. At runtime, List<String> and List<Integer> are both just List. This is why you cannot use instanceof List<String> or do new T().

PECS: if the structure gives you data → extends. If you put data in → super. If you both read and write → use the concrete type T.

11 What is Optional and how should (and shouldn't) you use it? Medium

Optional<T> is a container that explicitly signals a method may return no value. It was designed for return types — not to replace every nullable variable.

// ✅ Correct — return type that may have no result
Optional<User> findByEmail(String email) { ... }

findByEmail("a@b.com")
  .map(User::getName)
  .filter(n -> n.startsWith("A"))
  .orElse("Unknown");

opt.ifPresent(u -> save(u));
opt.orElseGet(() -> expensiveFallback()); // lazy
opt.orElseThrow(() -> new NotFoundException());

// ❌ Anti-patterns
if (opt.isPresent()) { opt.get(); }  // same as null check — use map/ifPresent
opt.get();                            // throws NoSuchElementException if empty
Optional<T> field;                    // don't use in fields, params, or collections
Never use Optional as method parameters, field types, or inside collections. It adds overhead without benefit there. It's purely a return type contract that says "this might be absent — handle it explicitly."

Angular

1 How does Angular change detection work? When would you use OnPush? Hard

Default strategy: Angular runs change detection on every component in the tree after any async event (click, timer, HTTP response). It checks every binding from root to leaf.

OnPush strategy: Angular only checks a component when:
① Its input references change (not just mutated values)
② An event originates inside the component
③ An Observable it subscribes to via async pipe emits
④ ChangeDetectorRef.markForCheck() is called manually 

@Component({
  changeDetection: ChangeDetectionStrategy.OnPush
})
export class ProductCardComponent {
  @Input() product!: Product; // must pass new reference
}
OnPush dramatically reduces the number of checks in a large component tree. Combine it with immutable data patterns (spread/map) and Observables for maximum performance.
2 Explain Subject, BehaviorSubject, and ReplaySubject. When do you use each? Hard

Subject — hot observable. Multicasts to all current subscribers. Late subscribers miss previous values. Use for events (button clicks, user actions).

BehaviorSubject — requires an initial value. Emits the latest value immediately to new subscribers. Use for state (current user, selected item, theme).

ReplaySubject(n) — buffers the last n values. New subscribers receive the buffer immediately. Use for activity logs, recent searches.

// BehaviorSubject — most common for state
private user$ = new BehaviorSubject<User | null>(null);

setUser(u: User) { this.user$.next(u); }
getUser$() { return this.user$.asObservable(); } // hide .next()
Follow-up: "Why do you expose asObservable() from a service?" — Prevents consumers from calling .next() directly; only the service controls state mutations.
3 What is the difference between switchMap, mergeMap, concatMap, and exhaustMap? Hard

All four operators project each source emission into an inner Observable, but differ in how they handle overlapping inner observables:

switchMap mergeMap concatMap exhaustMap

switchMap — cancels the previous inner observable when a new emission arrives. Best for search/autocomplete (cancel stale requests).

mergeMap — runs all inner observables concurrently. Best for independent parallel tasks (upload multiple files).

concatMap — queues inner observables; waits for each to finish before starting the next. Best for ordered sequential operations.

exhaustMap — ignores new emissions while an inner observable is active. Best for form submit (prevent double-submit).

Mental model: switchMap = "latest wins", mergeMap = "all at once", concatMap = "queue them", exhaustMap = "busy, ignore".
4 How does Angular's dependency injection hierarchy work? Hard

Angular has a hierarchical injector tree. When a component requests a service, Angular walks up the injector tree until it finds a provider:

Root injector (providedIn: 'root') — one singleton for the whole app. Most services go here.

Module injector — services provided in a lazy-loaded module are scoped to that module. Each module gets its own injector child.

Component injector (providers: [MyService] on a component) — creates a new instance per component. Children share this instance; sibling components get their own.

@Component({
  providers: [CartService]  // new instance per this component subtree
})
export class CheckoutComponent {}
Follow-up: "How would you provide a service only for a specific route?" — Use a lazy-loaded module or Route.providers (Angular 14+).
5 How do you prevent memory leaks from RxJS subscriptions? Medium

Subscriptions that are never unsubscribed keep the component alive in memory even after it's destroyed — a classic Angular memory leak.

Option 1 — async pipe (recommended): Angular auto-subscribes and auto-unsubscribes. No manual cleanup needed.

Option 2 — takeUntilDestroyed (Angular 16+):

data$ = interval(1000).pipe(
  takeUntilDestroyed()  // auto-completes when component destroys
);

Option 3 — takeUntil with destroy subject (classic):

private destroy$ = new Subject<void>();

ngOnDestroy() { this.destroy$.next(); this.destroy$.complete(); }

this.service.data$.pipe(takeUntil(this.destroy$))
  .subscribe(d => this.data = d);
6 Reactive Forms vs Template-driven Forms — when do you use each? Easy

Reactive Forms — form model defined in the component class using FormGroup / FormControl. Strongly typed (Angular 14+). Easier to test, compose validators, and react to value changes programmatically. Preferred for any non-trivial form.

Template-driven Forms — model defined in the template via ngModel. Less boilerplate for very simple forms. Harder to test and compose complex validation. Depends on FormsModule.

Senior answer: always use Reactive Forms in enterprise apps. Template-driven forms lack composability and are harder to unit-test without a DOM.
7 What are Angular Signals and how do they compare to RxJS Observables? Hard

Signals (Angular 16+) are synchronous reactive primitives that always hold a current value and notify consumers when it changes. Unlike Observables, they require no subscription management.

// Writable signal
const count = signal(0);
count.set(5);
count.update(v => v + 1);
count();  // read value — calling it like a function

// Computed — derived, read-only, memoized
const double = computed(() => count() * 2);

// Effect — side effect that runs when signals change
effect(() => console.log(`Count: ${count()}`));
Signals Synchronous, always have a value Auto dependency tracking No subscribe/unsubscribe Fine-grained change detection RxJS Async & event streams Powerful operators (switchMap, debounce) Best for HTTP & WebSocket
Signals enable fine-grained reactivity — Angular tracks exactly which signals a template reads and only re-evaluates those expressions. This makes the OnPush performance strategy largely automatic.
8 How does lazy loading work in Angular and what are preloading strategies? Medium

Lazy loading defers downloading a route's JavaScript bundle until the user navigates there. The initial bundle stays small, improving Time to Interactive (TTI) for large apps.

// Standalone component — lazy loaded per route
{
  path: 'dashboard',
  loadComponent: () => import('./dashboard.component')
    .then(m => m.DashboardComponent)
},
// Feature routes — lazy load entire route set
{
  path: 'admin',
  loadChildren: () => import('./admin/admin.routes')
    .then(m => m.adminRoutes)
}

Preloading strategies — after the app boots, Angular can preload lazy bundles in the background so navigation feels instant:

// Preload all lazy modules silently after initial boot
provideRouter(routes, withPreloading(PreloadAllModules))
Analyze your bundle with ng build --stats-json + webpack-bundle-analyzer. Every route not needed on the landing page is a lazy-loading candidate. Aim to keep the initial bundle under 200 KB gzipped.

10 What are standalone components and why are they the preferred approach now? Medium

Standalone components (Angular 14+, default in 17+) eliminate NgModules. Each component declares its own imports directly, making them self-contained and simpler to understand, lazy-load, and test.

@Component({
  standalone: true,                                 // no NgModule needed
  selector: 'app-user-card',
  imports: [CommonModule, RouterLink, DatePipe],  // explicit, tree-shakable
  template: `
    <a [routerLink]="['/user', user.id]">
      {{ user.name }} · {{ user.createdAt | date }}
    </a>`
})
export class UserCardComponent {
  @Input() user!: User;
}

Benefits: Better tree-shaking (unused imports are visible), per-component lazy loading, less boilerplate, simpler unit tests (no full TestBed module setup).

Interviewers at companies using Angular 17+ expect you to know standalone. NgModules still work but are the legacy path. New code should always use standalone.

React

1 What is the Virtual DOM and how does reconciliation work? Medium

The Virtual DOM is a lightweight in-memory representation of the real DOM tree. React builds a new VDOM on every render, then diffs it against the previous one (reconciliation) to find the minimal set of real DOM changes needed.

Reconciliation algorithm (Fiber): React compares nodes by type and key. Same type → update props. Different type → unmount old, mount new. Keys let React match list items across renders without re-mounting all of them.

Batching (React 18): Multiple state updates in the same event are batched into one render automatically — including inside timeouts and promises.

Follow-up: "Why is the key prop important in lists?" — Without stable keys, React may incorrectly reuse DOM nodes, causing wrong component state to appear on wrong items.
2 What is a stale closure in React hooks and how do you avoid it? Hard

A stale closure happens when a function inside useEffect (or useCallback) captures a variable from a previous render because the dependency array was incomplete or empty.

// ❌ Stale closure — count is always 0 inside setInterval
useEffect(() => {
  const id = setInterval(() => console.log(count), 1000);
  return () => clearInterval(id);
}, []);  // empty dep — count captured at mount (0)

// ✅ Fix 1 — add count to deps (restarts interval each change)
}, [count]);

// ✅ Fix 2 — functional updater (no need to read count)
setInterval(() => setCount(c => c + 1), 1000);
The ESLint rule react-hooks/exhaustive-deps catches most stale closure bugs. Never disable it without a clear reason.
3 What is the difference between useEffect and useLayoutEffect? Medium

useEffect — runs after the browser has painted. Asynchronous. The user sees the new render before the effect runs. Suitable for data fetching, subscriptions, analytics.

useLayoutEffect — runs synchronously after DOM mutations but before the browser paints. Blocks paint until the effect completes. Use only when you need to measure DOM elements or perform DOM mutations that must be invisible to the user (avoiding flicker).

// useLayoutEffect — measure DOM before paint
useLayoutEffect(() => {
  const { width } = ref.current.getBoundingClientRect();
  setWidth(width);  // update before browser paints — no flicker
}, []);
Default to useEffect. Switch to useLayoutEffect only if you see visual flickering caused by a DOM read/write that happens after paint.
4 How do React.memo, useCallback, and useMemo work together? Hard

React.memo wraps a component and skips re-rendering if its props are shallowly equal. But it breaks if a parent passes a new function or array reference every render — because objects are never === by reference.

useCallback memoizes a function so its reference is stable across renders. Needed when passing callbacks to memo-wrapped children.

useMemo memoizes a computed value so its reference is stable. Needed when passing objects/arrays as props to memo-wrapped children.

// All three work together or the optimization is useless
const handleClick = useCallback(() => doSomething(id), [id]);
const config = useMemo(() => ({ theme, lang }), [theme, lang]);

return <MemoizedChild onClick={handleClick} config={config} />;
If you add React.memo but forget useCallback/useMemo, the child still re-renders on every parent render because the prop references change. All three must be used together.
5 When would you reach for an external state manager (Redux, Zustand, Jotai) vs React's built-in state? Medium

Built-in state is enough when: state is local to a component or a small subtree; sharing is solved by lifting state or Context; the app is small-to-medium.

Reach for external state when:

Many components across the tree need the same state State updates from server (WebSocket, polling) need to reach many components You need time-travel debugging or strict state audit trails Context re-renders are causing performance issues State logic is complex and needs to be testable in isolation
Prefer Zustand for simplicity, Jotai for atom-level granularity, Redux Toolkit for large teams that need strict conventions. Avoid Redux for small/medium apps.
6 What are React Server Components (RSC) and how do they differ from client components? Hard

Server Components run only on the server. They can directly access databases, file system, and secrets. They produce zero JavaScript in the client bundle. They cannot use useState, useEffect, or browser APIs.

Client Components ('use client') are pre-rendered on the server and then hydrated on the client. They can use all hooks and browser events.

The model: Server Components are the default in Next.js App Router. They fetch data and compose the shell; they pass serializable props down to Client Components for interactivity.

// page.tsx — Server Component, runs on server only
export default async function ProductPage({ params }) {
  const product = await db.products.find(params.id); // direct DB!
  return <ProductDetail product={product} />; // may be client
}
7 What are forwardRef and useImperativeHandle and when do you need them? Medium

forwardRef — by default a ref on a custom component does nothing. forwardRef lets a parent reach inside a child to attach a ref to a specific DOM element.

// Child forwards the ref to its internal input
const FancyInput = React.forwardRef((props, ref) => (
  <input ref={ref} className="fancy" {...props} />
));

// Parent focuses the internal DOM input directly
const ref = useRef(null);
<FancyInput ref={ref} />
ref.current?.focus();

useImperativeHandle — instead of exposing the raw DOM node, expose a custom controlled API:

useImperativeHandle(ref, () => ({
  focus: () => inputRef.current?.focus(),
  clear: () => setValue(''),
}));
Prefer props and callbacks over refs for communication. Use forwardRef only when you genuinely need imperative DOM control — focus management, scroll, animations, measuring layout.
8 How do you test React components effectively? What makes a good test? Medium

The standard stack is Vitest (or Jest) + React Testing Library (RTL). RTL's core principle: test what the user sees and does — not component internals like state values or method calls.

// ✅ Test behavior, not implementation details
it('shows error when email is invalid', async () => {
  render(<LoginForm />);
  await userEvent.type(screen.getByLabelText('Email'), 'not-valid');
  await userEvent.click(screen.getByRole('button', { name: 'Log in' }));
  expect(screen.getByText('Invalid email')).toBeInTheDocument();
});
getByRole — preferred, tests accessibility too getByLabelText — for form inputs queryBy* — when element may not exist findBy* — for async content (returns promise)
Use MSW (Mock Service Worker) to intercept HTTP at the network level. Your components and hooks run with real fetch/axios — tests are realistic and resilient to implementation changes.
9 Controlled vs uncontrolled components — when do you use each? Easy

Controlled — React state is the single source of truth. Every keystroke fires onChange → setState. Enables instant validation, conditional logic, and derived UI.

Uncontrolled — the DOM manages its own state. React reads the value via useRef only when needed (e.g., on submit). Fewer re-renders, simpler for basic forms.

// Controlled
const [email, setEmail] = useState('');
<input value={email} onChange={e => setEmail(e.target.value)} />

// Uncontrolled — read on submit
const emailRef = useRef<HTMLInputElement>(null);
<input ref={emailRef} defaultValue="" />
// on submit: emailRef.current?.value
Use React Hook Form for large forms — it uses uncontrolled inputs internally for performance but exposes a controlled-like ergonomic API with validation built in.
10 How does concurrent rendering work in React 18 and what problems does it solve? Hard

Before React 18, rendering was synchronous — once started, React had to finish before the browser could respond to input. Large trees or expensive computations blocked the UI thread.

Concurrent rendering makes renders interruptible. React can pause a low-priority render to handle a high-priority update (a keystroke), then resume. The UI stays responsive even during heavy computation.

// useTransition — mark expensive update as non-urgent
const [isPending, startTransition] = useTransition();
<input onChange={e => {
  setInputValue(e.target.value);           // urgent — immediate
  startTransition(() =>
    setFilteredList(filterItems(e.target.value)) // deferred
  );
}} />
{isPending && <Spinner />}

// useDeferredValue — defer a value derived from props
const deferredQuery = useDeferredValue(searchQuery);
Add useTransition and useDeferredValue only where you've measured a real responsiveness problem. They add complexity — don't reach for them preemptively.

Full-Stack & API

1 JWT vs session-based authentication — trade-offs. Hard

Session-based: Server stores session in memory/database. Client gets a session ID cookie. Easy to revoke (delete the session). Stateful — problematic at scale across multiple servers (need sticky sessions or shared store like Redis).

JWT: Stateless — server encodes claims in a signed token. No server storage needed. Scales horizontally with no shared state. Hard to revoke before expiry (need a blocklist or short expiry + refresh tokens).

JWT Pros Stateless, scales easily Works across microservices / domains JWT Cons Can't revoke without extra infrastructure Token size in every request
Never store JWTs in localStorage (XSS risk). Use HttpOnly cookies. Keep expiry short (15 min) and implement refresh tokens stored in HttpOnly cookies.
2 What is the N+1 query problem and how do you solve it? Medium

The N+1 problem occurs when fetching a list of N records then executing a separate query per record to fetch related data — resulting in 1 + N queries total.

// ❌ N+1: 1 query for orders, then 1 per order for user
List<Order> orders = orderRepo.findAll();   // 1 query
for (Order o : orders) {
    User u = userRepo.findById(o.getUserId()); // N queries!
}

// ✅ Fix: JOIN FETCH (JPA) or batch loading
@Query("SELECT o FROM Order o JOIN FETCH o.user")

Solutions: JOIN FETCH (JPA), @EntityGraph, batch loading, DataLoader (GraphQL), or projecting only the needed fields from the start.

Always log SQL in development (show-sql: true in Spring). N+1 is invisible until you look at the query log or use a profiler like Hibernate Statistics.
3 What caching strategies do you know and when do you apply them? Hard

Cache-aside (Lazy loading): App checks cache first; on miss, loads from DB and populates cache. Most common. Risk: cache stampede on cold start.

Write-through: Every write goes to cache and DB together. Cache is always fresh. Higher write latency.

Write-behind (Write-back): Write to cache, async flush to DB. Fast writes, risk of data loss on crash.

Read-through: Cache is in front of DB. App only talks to cache; cache handles DB reads.

CDN — static assets, public pages Redis — sessions, rate limiting, leaderboards HTTP Cache-Control — browser and proxy caching Spring @Cacheable — method-level result caching DB query cache — repeated read-heavy queries
4 How do you design a secure REST API? Hard

Security is layered. A strong senior answer covers all layers:

Auth & AuthZ: JWT/OAuth2 for authentication. Role-based or attribute-based access control on every endpoint. Never trust the client for authorization decisions.

Transport: HTTPS everywhere. HSTS headers. No sensitive data in URLs (goes to logs).

Input validation: Validate and sanitize all input at the boundary. Use parameterized queries — never build SQL from strings. Reject unexpected fields.

Rate limiting: Throttle by IP and by user to prevent brute-force and DDoS.

Sensitive data: Never log passwords, tokens, PII. Encrypt at rest. Hash passwords with bcrypt/Argon2.

Headers: Content-Security-Policy, X-Content-Type-Options, X-Frame-Options, CORS restricted to known origins.

OWASP Top 10 is a reliable checklist. Interviewers expect you to name broken access control, injection, security misconfiguration, and insecure design.
5 SQL vs NoSQL — how do you choose? Medium

Choose SQL (PostgreSQL, MySQL) when: data is relational and normalized; you need ACID transactions across multiple tables; schema is well-defined and stable; complex queries with joins are needed.

Choose NoSQL when: schema is flexible or evolves rapidly; horizontal scale and high write throughput are priorities; data naturally fits documents (MongoDB), key-value (Redis), wide-column (Cassandra), or graphs (Neo4j).

Senior answer: "I've used both in the same system." PostgreSQL for transactional data, Redis for caching/sessions, Elasticsearch for full-text search. The database type should match the access pattern, not company preference.
6 What is CORS and how do you configure it correctly? Medium

CORS (Cross-Origin Resource Sharing) is a browser security policy that blocks requests from one origin (domain/port/protocol) to another unless the server explicitly permits it via HTTP response headers.

Simple requests (GET, POST with form types) are sent directly and the browser checks the response. Preflighted requests (PUT, DELETE, JSON body, custom headers) send an OPTIONS check first.

// Spring Boot — global CORS configuration
@Bean
CorsConfigurationSource corsConfig() {
  var config = new CorsConfiguration();
  config.setAllowedOrigins(List.of("https://myapp.com")); // never use * with credentials
  config.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE"));
  config.setAllowedHeaders(List.of("Authorization", "Content-Type"));
  config.setAllowCredentials(true);
  var source = new UrlBasedCorsConfigurationSource();
  source.registerCorsConfiguration("/**", config);
  return source;
}
Never combine Access-Control-Allow-Origin: * with Access-Control-Allow-Credentials: true — browsers reject this. Credentials require an explicit origin, not a wildcard.
7 REST vs GraphQL vs gRPC — when do you choose each? Hard

REST — resource-based, uses HTTP methods and standard status codes. Ubiquitous, cacheable, browser-native. Suffers from over-fetching (too much data) and under-fetching (too many requests). Best for: public APIs, simple CRUD, standard web apps.

GraphQL — client specifies exactly what data it needs in one query. Eliminates over/under-fetching. Single endpoint. Best for: complex frontend data needs, multiple clients (mobile vs web) needing different shapes, rapid UI iteration.

gRPC — binary protocol (Protocol Buffers), HTTP/2, strict contract via .proto files. Extremely fast and efficient. Best for: internal microservice-to-service communication, high-throughput systems, polyglot environments where type safety across languages matters.

The common pattern: REST for public/external APIs, GraphQL when the frontend has complex varied data needs, gRPC for internal service communication. Many mature systems use all three in different layers.
8 How do you handle database migrations safely in a live production system? Hard

Migrations on a live system risk downtime, data loss, or table locks. The senior approach is the expand-contract pattern (also called online migrations).

1. Expand — add new column/table as nullable, backward-compatible 2. Migrate — backfill data; app writes to both old and new 3. Contract — remove old column in a later release after all code updated

Tools: Flyway or Liquibase for versioned migrations — each migration is a numbered SQL file in version control, run automatically on deploy.

-- Always add indexes CONCURRENTLY in PostgreSQL — no table lock
CREATE INDEX CONCURRENTLY idx_users_email ON users(email);

-- Never rename a column directly — use expand-contract instead
-- Step 1: ALTER TABLE users ADD COLUMN email_address TEXT;
-- Step 2: backfill + update app
-- Step 3: ALTER TABLE users DROP COLUMN email;
Never rename a column in one step on a live system — old code deployments will break. Expand-contract ensures every deployment stage is backward-compatible.
9 What is optimistic vs pessimistic locking and when do you use each? Hard

Pessimistic locking — locks the row on read using SELECT FOR UPDATE. No other transaction can modify it until you commit. Guarantees consistency but reduces throughput and risks deadlocks under high concurrency.

Optimistic locking — no lock on read. On update, check a version or updated_at column; if it changed since you read it, abort and retry. High throughput, no deadlocks, but requires retry logic.

-- Pessimistic: lock the row for the duration of the transaction
SELECT * FROM orders WHERE id = 1 FOR UPDATE;
UPDATE orders SET status = 'SHIPPED' WHERE id = 1;

-- Optimistic: JPA @Version handles it automatically
@Entity class Order {
  @Version private long version; // auto-checked and incremented on save
}
// Throws OptimisticLockException if another transaction updated first
Rule of thumb: use optimistic locking when conflicts are rare (most web apps). Use pessimistic locking when conflicts are frequent or the cost of retrying is high — inventory reservation, seat booking, financial transactions.

System Design & Architecture

1 How would you design a URL shortener (like bit.ly)? Hard

Core flow: User submits long URL → generate unique short code → store mapping → redirect on access.

Short code generation: Base62 encoding of an auto-incremented ID, or hash (MD5/SHA256) of the URL truncated to 6–8 chars (check collision). Distributed: use a dedicated ID generator service (Snowflake-style) to avoid DB contention.

Storage: Key-value store (Redis or DynamoDB) for ultra-fast reads. Key = short code, value = long URL.

Redirect: HTTP 301 (permanent, cached by browser) vs 302 (temporary, every request hits server — better for analytics).

Scale: Cache hot URLs in memory. CDN at the edge for the most popular codes. Read replicas for DB. Shard by first character of code.

Interviewer evaluates: requirements clarification, estimation (QPS, storage), trade-offs, not "the perfect answer".
2 Explain CAP theorem and where your past projects landed. Hard

In a distributed system you can guarantee at most two of three properties simultaneously:

C — Consistency: Every read returns the most recent write or an error.

A — Availability: Every request receives a response (may not be the latest data).

P — Partition tolerance: System keeps working even if some nodes can't communicate.

Since network partitions happen in production, you must choose CP or AP:

CP systems

HBase, Zookeeper, MongoDB (w/ strong consistency). Refuse requests during partition.

AP systems

Cassandra, CouchDB. Always available but may return stale data. Eventual consistency.

Be ready to say where your past project sat: "We used PostgreSQL — CP. During a partition we preferred correctness over availability. That was fine for our banking use case."
3 How do you implement rate limiting? Medium

Token bucket: Each user has a bucket of N tokens refilled at a fixed rate. Each request consumes a token. Allows bursts up to bucket size. Most common algorithm.

Sliding window counter: Track request counts in rolling time windows. More accurate than fixed window (which allows 2× burst at window boundaries).

Implementation: Redis with atomic Lua scripts or INCR + EXPIRE for distributed rate limiting. Apply in an API gateway (Kong, AWS API Gateway) or in a Spring filter.

// Redis token bucket — atomic INCR with TTL
MULTI
  INCR user:123:requests
  EXPIRE user:123:requests 60  // 60-second window
EXEC
// Return 429 if count > limit
4 What is eventual consistency and how do you handle it in the frontend? Hard

Eventual consistency means all replicas of data will converge to the same value eventually, but a read immediately after a write might return stale data. Common in distributed databases (Cassandra, DynamoDB), CDNs, and microservice event-driven architectures.

Frontend strategies:

Optimistic updates — update UI immediately, rollback on error Polling — re-fetch after a delay to get the settled value WebSocket — push updates when server settles Read-your-writes — route reads back to the same replica as writes Version tokens — server returns a version; client retries until version matches
React Query and SWR implement optimistic updates and automatic refetch out of the box — mention these as production-ready solutions.
5 Microservices vs Monolith — how do you choose and how do you decompose? Hard

Start with a monolith unless you have clear scale or team-autonomy requirements. A monolith is simpler to develop, test, deploy, and reason about. Premature decomposition is one of the most expensive architectural mistakes.

Decompose when: teams are large enough to own services independently; a specific domain needs different scaling, deployment cadence, or tech stack; bounded contexts are clearly identified.

Decomposition strategies: by business capability (Orders, Inventory, Auth), by bounded context (DDD), by subdomain volatility (stable core vs frequently-changing modules).

Hidden costs of microservices: network latency, distributed transactions (Saga pattern), observability complexity, service discovery, data consistency across services.

The senior answer: "We started with a modular monolith, identified the two services with different scaling profiles, and extracted only those." Avoid "we did microservices from day one."
6 How would you design a real-time notification system (like Slack or Gmail alerts)? Hard

Clarify first: What channels (in-app, email, push, SMS)? What latency is acceptable? What's the volume? Are notifications per-user or broadcast?

Core architecture:

1. Event producer — service emits event (order shipped, mention, etc.) 2. Message queue (Kafka/SQS) — decouples producers from notification service 3. Notification service — reads queue, applies user preferences, routes to channel 4. Channel workers — email (SES), push (FCM/APNs), SMS (Twilio) 5. Real-time delivery — WebSocket or SSE for in-app live updates

Real-time delivery: Each user's browser holds a WebSocket connection to a notification gateway. The gateway subscribes to a Redis pub/sub channel keyed by user ID. When an event arrives, Redis fans it out to the right gateway instance.

Show production awareness: deduplication (idempotency keys), user preferences (mute, digest mode), delivery tracking, retry with exponential backoff, dead-letter queues for failed channels.
7 What is a message queue and when should you use one instead of a direct API call? Medium

A message queue (Kafka, RabbitMQ, SQS) stores messages durably until they're processed. The producer fires and forgets — it doesn't wait for the consumer to finish.

Use a queue when Consumer is slow or doesn't need to respond immediately Absorbing traffic spikes (order processing, email, image resize) Multiple services react to the same event (fan-out) Guaranteed delivery & retry on failure is required Work can be distributed across multiple consumer instances
Keep as direct API when Caller needs the result synchronously Strong consistency is required across the call The request-response model fits naturally
Queues add operational complexity: ordering guarantees, dead-letter queues, idempotency, at-least-once delivery. Don't add a queue just because it sounds modern — justify the trade-off.
8 Explain database indexing strategies — when to add, what to index, trade-offs. Hard

An index (typically a B-tree) lets the database find rows without scanning the full table. Every index speeds reads but slows writes and consumes storage.

Columns in WHERE clauses (high-cardinality first) Foreign key columns (avoid full scans on JOINs) Columns in ORDER BY / GROUP BY Composite index — column order must match query pattern (leftmost prefix) 
-- Composite index — order matters for query coverage
CREATE INDEX idx_orders ON orders(user_id, status, created_at);
-- ✅ WHERE user_id = ? AND status = ?  (uses index)
-- ✅ WHERE user_id = ?                (uses index — leftmost prefix)
-- ❌ WHERE status = ?                 (skips first column — no index use)

-- Covering index — entire query satisfied from the index alone
CREATE INDEX idx_cover ON orders(user_id) INCLUDE (total, status);
-- SELECT total, status WHERE user_id = ? — no table heap access
Too many indexes on a write-heavy table kills write performance. Profile with EXPLAIN ANALYZE (PostgreSQL) before and after. Only add indexes you can justify with query evidence.
9 How do you design a system for high availability (99.9%+)? Hard

HA means the system stays operational despite component failures. 99.9% = ~8.7 hours downtime/year. 99.99% = ~52 minutes/year.

Eliminate single points of failure — every layer is redundant Load balancers with health checks — remove unhealthy instances DB primary + read replicas with automatic failover Multi-AZ deployment — survive a full datacenter failure Circuit breakers — stop cascade failures (Resilience4j, Hystrix) Graceful degradation — serve partial content when a dependency fails Kubernetes self-healing — restarts crashed pods automatically Chaos engineering — inject failures in staging to test resilience
Senior framing: calculate your error budget (e.g. 99.9% SLA = 43 min/month allowable downtime), identify which failure scenarios consume the most of that budget, and invest engineering effort there first — not evenly across all failure modes.

2 How do you handle technical debt? Medium

Technical debt is normal — the problem is untracked or accumulating debt. A senior engineer manages it deliberately:

Track it — create tickets, don't just mention it in standups Classify it — deliberate vs accidental vs outdated Quantify the cost — "this adds 2 hours to every feature in module X" Negotiate time — "20% capacity for tech debt every sprint" Boy-scout rule — always leave the code cleaner than you found it Pay it down incrementally — avoid big bang rewrites

5 How do you make architectural decisions and get buy-in? Hard

This is a core senior competency — moving from "I write good code" to "I shape how the team builds software."

Decision process: Define the problem and success criteria first. Research alternatives with trade-offs documented. Write an RFC or Architecture Decision Record (ADR). Present to stakeholders with a recommendation, not a list of options.

Getting buy-in: Involve seniors early (don't present a finished plan). Connect the decision to business goals (cost, speed, risk). Address concerns directly. Time-box the decision to avoid analysis paralysis.

// ADR structure (Architecture Decision Record)
Title: Use Redis for session storage
Status: Accepted | Proposed | Deprecated
Context: why this decision is needed
Decision: what we chose
Alternatives: what we rejected and why
Consequences: trade-offs accepted
Mention ADRs by name — they signal that you think in terms of documented, reversible decisions, not tribal knowledge.

7 How do you approach code reviews — giving and receiving feedback? Medium

Giving reviews: Start with the goal — is this safe to ship? Does it meet requirements? Prioritize correctness and security over style. Use questions instead of demands: "What happens if this value is null?" vs "Handle the null case." Be explicit about what's a blocker vs a suggestion.

Blocker: correctness bugs, security issues, breaking API changes Suggestion: readability, performance (non-critical), style Praise: note elegant solutions — builds a healthy review culture

Receiving reviews: Treat feedback as feedback on the code, not on you. Ask for clarification on vague comments. If you disagree, explain your reasoning — don't just quietly comply or dig in. Acknowledge when someone caught something real.

At the senior level, the best code reviews teach the author something — even when you're approving. That's how standards spread across a team without being mandated.
