Components & Props

Functional component anatomy

// Props typed with an interface
interface ButtonProps {
  label: string;
  onClick: () => void;
  disabled?: boolean;   // optional
}

function Button({ label, onClick, disabled = false }: ButtonProps) {
  return (
    <button onClick={onClick} disabled={disabled}>
      {label}
    </button>
  );
}
Prefer destructuring props directly in the function signature. Default values replace defaultProps, which is deprecated.

JSX rules

// 1. Must return a single root — use Fragment if needed
return (
  <>
    <h1>Title</h1>
    <p>Body</p>
  </>
);

// 2. className not class, htmlFor not for
<label htmlFor="email">Email</label>

// 3. Self-close empty tags
<img src={url} alt="hero" />

// 4. Expressions in {}, not statements
<p>{isAdmin ? 'Admin' : 'User'}</p>

children & composition

// Accepts any renderable children
function Card({ children, title }: { children: React.ReactNode; title: string }) {
  return (
    <div className="card">
      <h2>{title}</h2>
      {children}
    </div>
  );
}

// Usage
<Card title="Hello">
  <p>Content here</p>
</Card>
Prefer composition (passing children) over deeply nested props drilling. It avoids coupling and makes components reusable.

Lists & keys

const items = ['Apple', 'Banana', 'Cherry'];

<ul>
  {items.map((item, i) => (
    <li key={item}>{item}</li>   // stable id > index
  ))}
</ul>
Never use array index as key when items can be reordered or deleted — it confuses React's reconciler and causes bugs.

State & useState

useState basics

import { useState } from 'react';

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(c => c + 1)}>
      Count: {count}
    </button>
  );
}
Use the functional updater setCount(c => c + 1) when next state depends on previous — avoids stale closure bugs.

Object & array state — never mutate!

// ❌ Wrong — mutates existing state
state.name = 'Ana';
setState(state);

// ✅ Correct — spread to create new reference
setState(prev => ({ ...prev, name: 'Ana' }));

// ✅ Arrays — filter / map / spread
setItems(prev => [...prev, newItem]);           // add
setItems(prev => prev.filter(i => i.id !== id)); // remove
setItems(prev => prev.map(i =>
  i.id === id ? { ...i, done: true } : i      // update one
));

Controlled forms

const [email, setEmail] = useState('');

<input
  type="email"
  value={email}
  onChange={e => setEmail(e.target.value)}
/>

State drives the input value; every keystroke updates state and re-renders. The input is always in sync with the model.

State rules

State triggers a re-render State is local to the component instance Lift state up to share it between siblings Don't derive state — compute it from existing state useState initializer runs only on first render

Effects & useEffect

useEffect patterns

import { useEffect } from 'react';

// Runs after every render
useEffect(() => { document.title = title; });

// Runs once on mount
useEffect(() => { fetchData(); }, []);

// Runs when userId changes
useEffect(() => { fetchUser(userId); }, [userId]);

// Cleanup — runs before next effect or on unmount
useEffect(() => {
  const id = setInterval(tick, 1000);
  return () => clearInterval(id);   // cleanup
}, []);
Include every reactive value used inside the effect in the dependency array, or the effect will read stale values.

Data fetching with useEffect

const [data, setData] = useState(null);
const [loading, setLoading] = useState(true);

useEffect(() => {
  let cancelled = false;       // prevent stale update

  fetch(`/api/posts/${id}`)
    .then(r => r.json())
    .then(d => { if (!cancelled) setData(d); })
    .finally(() => { if (!cancelled) setLoading(false); });

  return () => { cancelled = true; };
}, [id]);
In React 18+ with Strict Mode, effects run twice in development. Design effects to be idempotent and always provide cleanup.

When NOT to use useEffect

Don't

Derive state from props — compute it directly in render.

Don't

Sync parent state — use event handlers instead.

Do

Sync with external systems (timers, subscriptions, DOM).

Do

Fetch data that depends on component lifecycle.

Essential hooks

useRef

// 1. DOM access
const inputRef = useRef<HTMLInputElement>(null);
<input ref={inputRef} />
const focus = () => inputRef.current?.focus();

// 2. Mutable value that doesn't trigger re-render
const renderCount = useRef(0);
renderCount.current++;   // persists across renders, no re-render

useMemo & useCallback

// useMemo — memoize expensive computation
const sorted = useMemo(
  () => [...items].sort((a, b) => a.name.localeCompare(b.name)),
  [items]   // recompute only when items changes
);

// useCallback — stable function reference
const handleDelete = useCallback(
  (id: number) => setItems(prev => prev.filter(i => i.id !== id)),
  []   // no dependencies — function is created once
);
Don't premature-optimise. Only add useMemo/useCallback when you can measure a performance problem — they add complexity and cost memory.

Custom hooks

// Extract reusable stateful logic into a hook
function useLocalStorage<T>(key: string, initial: T) {
  const [value, setValue] = useState<T>(() => {
    const stored = localStorage.getItem(key);
    return stored ? JSON.parse(stored) : initial;
  });

  const set = useCallback((v: T) => {
    setValue(v);
    localStorage.setItem(key, JSON.stringify(v));
  }, [key]);

  return [value, set] as const;
}

// Usage
const [theme, setTheme] = useLocalStorage('theme', 'light');
Hook names must start with use. Hooks can call other hooks — this is how you compose behaviour.

Hook rules

Only call hooks at the top level — no conditions or loops Only call hooks inside React functions or custom hooks Same hook order every render (React relies on call order)

Context & useReducer

Context — share state without prop drilling

// 1. Create
const ThemeContext = createContext<'light' | 'dark'>('light');

// 2. Provide
function App() {
  const [theme, setTheme] = useState<'light' | 'dark'>('light');
  return (
    <ThemeContext.Provider value={theme}>
      <Layout />
    </ThemeContext.Provider>
  );
}

// 3. Consume (anywhere in the tree)
function Header() {
  const theme = useContext(ThemeContext);
  return <header className={theme}>...</header>;
}
Context re-renders every consumer when the value changes. Split contexts by concern (AuthContext, ThemeContext) to limit unnecessary re-renders.

useReducer — for complex state logic

type Action =
  | { type: 'increment' }
  | { type: 'decrement' }
  | { type: 'reset'; payload: number };

function reducer(state: number, action: Action): number {
  switch (action.type) {
    case 'increment': return state + 1;
    case 'decrement': return state - 1;
    case 'reset':     return action.payload;
    default: return state;
  }
}

const [count, dispatch] = useReducer(reducer, 0);
dispatch({ type: 'increment' });
Use useReducer when state has multiple sub-values or when the next state depends on the previous in complex ways. Combine with Context to avoid a full Redux setup for local-ish state.

Context + useReducer pattern (lightweight global state)

const StateContext = createContext<State>(null!);
const DispatchContext = createContext<Dispatch<Action>>(null!);

function StoreProvider({ children }: { children: React.ReactNode }) {
  const [state, dispatch] = useReducer(reducer, initialState);
  return (
    <StateContext.Provider value={state}>
      <DispatchContext.Provider value={dispatch}>
        {children}
      </DispatchContext.Provider>
    </StateContext.Provider>
  );
}

Performance

React.memo — skip re-renders of pure components

// Without memo: re-renders whenever parent re-renders
// With memo: re-renders only when props change (shallow compare)
const Avatar = React.memo(function Avatar({ url, size }: AvatarProps) {
  return <img src={url} width={size} />;
});

// Custom comparison — return true to SKIP re-render
const Row = React.memo(Component, (prev, next) =>
  prev.id === next.id && prev.selected === next.selected
);
React.memo + useCallback for the handler + useMemo for derived data is the trio for memoisation. Use together or the benefit disappears.

Code splitting & lazy loading

import { lazy, Suspense } from 'react';

// Bundle is split — loaded only when component is rendered
const Dashboard = lazy(() => import('./pages/Dashboard'));

function App() {
  return (
    <Suspense fallback={<Spinner />}>
      <Dashboard />
    </Suspense>
  );
}

What causes a re-render?

Triggers

setState called · parent re-renders · context value changes · useReducer dispatch

Prevent

React.memo · stable props via useCallback/useMemo · split context · key stability

Profile first with React DevTools Profiler before optimising — premature memoisation adds complexity with no benefit.

useTransition & useDeferredValue (React 18+)

// Mark a state update as non-urgent
const [isPending, startTransition] = useTransition();
startTransition(() => setSearchQuery(input));

// Defer an expensive derived value
const deferred = useDeferredValue(searchQuery);
React renders urgent updates (typing) first and defers slow ones (filtering a huge list), keeping the UI responsive.

Routing (React Router v6)

Route configuration

// main.tsx
createBrowserRouter([
  {
    path: '/',
    element: <RootLayout />,
    children: [
      { index: true, element: <Home /> },
      { path: 'users/:id', element: <UserDetail /> },
      {
        path: 'admin',
        element: <ProtectedRoute />,
        children: [
          { path: 'dashboard', element: <Dashboard /> },
        ]
      },
      { path: '*', element: <NotFound /> },
    ]
  }
])

Navigation & params

import { useNavigate, useParams, Link } from 'react-router-dom';

function UserDetail() {
  const { id } = useParams();          // /users/42 → id = "42"
  const navigate = useNavigate();

  return (
    <>
      <p>User {id}</p>
      <Link to="/">Home</Link>
      <button onClick={() => navigate(-1)}>Back</button>
    </>
  );
}
Use <Link> for declarative navigation (renders an <a>) and useNavigate for programmatic navigation after form submit, auth, etc.

Protected routes & loaders

// Protected route wrapper
function ProtectedRoute() {
  const { user } = useAuth();
  return user ? <Outlet /> : <Navigate to="/login" replace />;
}

// Data loader (React Router 6.4+)
{ path: 'users/:id', element: <UserDetail />,
  loader: ({ params }) => fetch(`/api/users/${params.id}`) }

// In component
const user = useLoaderData() as User;

Patterns to know

Error boundaries

// Class component — only way to catch render errors
class ErrorBoundary extends Component {
  state = { hasError: false };
  static getDerivedStateFromError() { return { hasError: true }; }
  componentDidCatch(err: Error, info: ErrorInfo) { logError(err, info); }
  render() {
    return this.state.hasError
      ? <h2>Something went wrong.</h2>
      : this.props.children;
  }
}

// Usage — wrap subtrees you want to isolate
<ErrorBoundary><Dashboard /></ErrorBoundary>
Use react-error-boundary on npm for a hooks-friendly version with reset callbacks.

Compound components

// Components that share implicit state via Context
<Select value={val} onChange={setVal}>
  <Select.Option value="a">Alpha</Select.Option>
  <Select.Option value="b">Beta</Select.Option>
</Select>

// Each Select.Option reads the parent's context
// to know if it's currently selected

Render props vs. hooks

Render props were the pattern before hooks. Hooks replaced most use cases but render props are still useful for inversion of control (e.g. virtualised lists, animation libraries).

// Old render-prop pattern
<Mouse render={({ x, y }) => <p>{x}, {y}</p>} />

// Modern hook equivalent
const { x, y } = useMouse();
