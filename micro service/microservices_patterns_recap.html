Decomposition patterns

Decompose by business capability

Split services around what the business does, not around technical layers. Each service owns one business capability end-to-end.

Monolith ├── OrderService → handles order lifecycle ├── InventoryService → stock and warehouse ├── PaymentService → billing and refunds ├── NotificationService → emails, SMS, push └── UserService → accounts and profiles
A service should be small enough for one team to own, and large enough to deploy independently without tight coupling to others.

Strangler fig pattern

Migrate a monolith incrementally: route new functionality to new microservices while the monolith still handles legacy paths. Strangle it over time — never big-bang rewrite.

Client → API Gateway → [ new: OrderService ] ↘ [ legacy: Monolith (orders) ] ← shrinks over time

Domain-driven design (DDD) concepts

Bounded context

A clear boundary where a domain model applies. Maps 1:1 to a service.

Aggregate

A cluster of objects treated as a unit. Each service manages its own aggregates.

Domain event

Something that happened in the domain (e.g. OrderPlaced). Drives async communication.

Anti-corruption layer

Translates between models at service boundaries — prevents domain leakage.

Communication patterns

Sync vs. async

Synchronous (REST / gRPC)

Caller waits for a response. Simple but creates tight temporal coupling. Use for queries where you need an immediate answer.

Asynchronous (messaging)

Caller fires and forgets. Services are decoupled in time. Use for commands and events where eventual consistency is acceptable.

Avoid long synchronous chains (A → B → C → D). One slow service cascades latency to all callers. Prefer async or cache aggressively.

Event-driven / messaging

// Producer publishes a domain event
kafkaTemplate.send("order-events", OrderPlacedEvent.builder()
    .orderId(order.getId())
    .customerId(order.getCustomerId())
    .total(order.getTotal())
    .build());

// Consumer reacts independently
@KafkaListener(topics = "order-events")
public void onOrderPlaced(OrderPlacedEvent event) {
    inventoryService.reserve(event.getOrderId());
}
Kafka — high-throughput, durable log RabbitMQ — flexible routing, AMQP AWS SQS/SNS — managed, serverless-friendly

Choreography vs. orchestration

Choreography

Services react to events independently. No central brain. Loose coupling, harder to trace.

Orchestration (Saga)

A coordinator (e.g. Saga orchestrator) directs each step. Easier to follow, single point of control.

Resilience patterns

Circuit breaker

Wraps a remote call. When failures exceed a threshold, the circuit opens and fast-fails requests (no more waiting). After a timeout it tries again (half-open).

@CircuitBreaker(name = "inventoryService", fallbackMethod = "fallback")
public Stock getStock(String productId) {
    return inventoryClient.getStock(productId); // may fail
}

public Stock fallback(String productId, Exception ex) {
    return Stock.unknown(); // graceful degradation
}
CLOSED → (failures > threshold) → OPEN → (timeout) → HALF-OPEN → (success) → CLOSED ↘ (failure) → OPEN

Retry with exponential backoff

@Retry(name = "paymentService", fallbackMethod = "fallback")
// resilience4j config:
// maxAttempts: 3
// waitDuration: 500ms
// enableExponentialBackoff: true  → 500ms, 1s, 2s
// retryExceptions: [IOException, TimeoutException]
Always add jitter to retries — without it, all instances retry simultaneously and create a retry storm that hammers the failing service even harder.

Bulkhead pattern

Isolate resources (thread pools, connection pools) per dependency. If one downstream service hangs, it only exhausts its own pool — not the whole application.

Thread pool bulkhead — separate thread pool per service Semaphore bulkhead — limit concurrent calls Rate limiter — cap requests per second Timeout — never wait forever

Saga pattern — distributed transactions

Replaces 2-phase commit. A saga is a sequence of local transactions. Each step publishes an event; on failure, compensating transactions undo prior steps.

OrderSaga: 1. OrderService.createOrder() → success → emit OrderCreated 2. PaymentService.charge() → success → emit PaymentCharged 3. InventoryService.reserve() → FAIL → emit ReservationFailed ↓ compensate backwards 2b. PaymentService.refund() 1b. OrderService.cancelOrder()
Sagas give you eventual consistency without distributed locks. Design compensating transactions from day one.

Data patterns

Database per service

Each service owns its database — no shared schema, no direct cross-service SQL joins. Services exchange data only through APIs or events.

OrderService → orders_db (PostgreSQL) InventoryService → inventory_db (MongoDB) UserService → users_db (MySQL) AnalyticsService → analytics_db (Redshift)
Cross-service queries become API calls or event joins. This is harder but prevents the tight coupling that shared DBs create.

CQRS — Command Query Responsibility Segregation

Separate the write model (commands that change state) from the read model (queries that return data). Each side can scale, optimise, and evolve independently.

Client → Command Handler → Write DB (normalised, consistent) ↓ publishes event Query Handler ← Read DB (denormalised, fast reads)

Event sourcing

Store state as an immutable sequence of events rather than current values. Replay events to rebuild any past or present state.

// Event store (append-only)
OrderCreated   { orderId, customerId, total }
ItemAdded      { orderId, productId, qty }
PaymentCharged { orderId, amount }
OrderShipped   { orderId, trackingId }

// Rebuild current state by replaying events
Order order = eventStore.getEvents(orderId)
    .reduce(Order.empty(), Order::apply);
Event sourcing pairs naturally with CQRS and gives you a full audit log and time-travel debugging for free.

Outbox pattern

Atomically save a DB record AND publish an event by writing the event to an outbox table in the same transaction. A separate relay process reads the outbox and publishes to the message broker.

BEGIN TRANSACTION INSERT INTO orders ... INSERT INTO outbox (event_type, payload) VALUES ('OrderPlaced', ...) COMMIT ↓ Outbox relay → Kafka → consumers
Never write to the DB and publish to a broker in two separate operations — if the broker call fails, you get inconsistency. The outbox pattern solves this.

API gateway and discovery

API gateway

Single entry point for all clients. Handles cross-cutting concerns so individual services don't have to.

Client → API Gateway → OrderService ↘ → PaymentService ↘ → UserService
Routing and load balancing Authentication and authorization Rate limiting SSL termination Request aggregation (BFF) Caching Logging and tracing
Backends for Frontends (BFF): create a dedicated gateway per client type (mobile, web, third-party) to tailor the API surface for each consumer.

Service discovery

Client-side discovery

Client queries a service registry (e.g. Eureka) and picks an instance. More control, registry dependency in each client.

Server-side discovery

Load balancer (e.g. AWS ALB, Kubernetes Service) handles routing. Clients are registry-unaware. Simpler clients.

Service mesh (Istio / Linkerd)

A dedicated infrastructure layer that handles service-to-service communication: mTLS, retries, timeouts, circuit breaking, and observability — without touching application code.

Service A (app) → sidecar proxy ──mTLS──→ sidecar proxy → Service B (app) ↕ metrics/traces ↕ Control plane (Istio / Linkerd)

Observability

The three pillars

Logs

Structured event records. Use JSON with a correlation ID in every log entry. Aggregate with ELK, Loki, or CloudWatch.

Metrics

Numeric time-series. Track error rate, latency (p50/p95/p99), throughput, saturation. Prometheus + Grafana.

Traces

End-to-end request journeys across services. Jaeger, Zipkin, or Tempo. Essential for debugging latency in distributed calls.

Correlation ID

A unique ID generated at the edge and propagated through every service call — ties logs, metrics, and traces together.

Distributed tracing

// Spring Boot + Micrometer Tracing (auto-propagates headers)
@GetMapping("/order/{id}")
public Order getOrder(@PathVariable String id) {
    // traceId + spanId auto-added to logs and outgoing HTTP
    var items = itemClient.getItems(id);    // child span
    var payment = paymentClient.get(id);   // child span
    return Order.of(items, payment);
}
TraceId: abc123 [OrderService ] GET /order/1 0–120ms [ItemService ] GET /items/1 5–60ms [PaymentService ] GET /payment/1 65–110ms

Health checks and readiness

# Spring Boot Actuator (auto-exposed)
GET /actuator/health       → { "status": "UP" }
GET /actuator/health/liveness   → Kubernetes liveness probe
GET /actuator/health/readiness  → Kubernetes readiness probe
GET /actuator/metrics     → Prometheus-compatible metrics
Separate liveness (is the process alive?) from readiness (is it ready to serve traffic?). A warming-up service should fail readiness but pass liveness — don't kill it, just stop sending it traffic.

Security patterns

JWT and OAuth 2.0 / OIDC flow

1. User logs in → Auth Server (Keycloak / Auth0) 2. Auth Server issues Access Token (JWT) + Refresh Token 3. Client sends: Authorization: Bearer <JWT> 4. API Gateway validates JWT signature (public key) 5. Gateway forwards claims (userId, roles) to downstream services 6. Services trust the gateway — no re-validation needed
Services should never validate tokens themselves in a microservices architecture — delegate to the gateway or a sidecar to avoid duplicated logic and key rotation headaches.

Zero trust — never trust, always verify

mTLS between services — mutual certificate auth Service accounts with minimal permissions Network policies — whitelist allowed traffic only Secrets management — Vault, AWS Secrets Manager, never env vars in code Audit logs for all service-to-service calls

Common attack surfaces

Broken auth

Ensure every endpoint validates the JWT and checks scopes/roles.

Excessive data exposure

Return only what the client needs — filter server-side, not client-side.

Injection

Validate and sanitise all inputs, even internal service calls.

Mass assignment

Use DTOs, never bind request body directly to domain objects.

Deployment patterns

Deployment strategies

Blue / green

Two identical environments. Switch traffic from blue (live) to green (new) instantly. Easy rollback — flip the switch back.

Canary release

Route a small percentage (e.g. 5%) to the new version. Gradually increase. Catches issues before full rollout.

Rolling update

Replace instances one by one. Zero downtime. Default in Kubernetes. Slower rollback.

Feature flags

Deploy code but gate features with runtime flags. Decouples deployment from release.

Kubernetes essentials for microservices

# Each service gets its own Deployment + Service
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxUnavailable: 1, maxSurge: 1 }
  template:
    spec:
      containers:
      - name: order-service
        image: myregistry/order-service:v2.1.0
        readinessProbe:
          httpGet: { path: /actuator/health/readiness, port: 8080 }
        livenessProbe:
          httpGet: { path: /actuator/health/liveness, port: 8080 }
        resources:
          requests: { cpu: 250m, memory: 256Mi }
          limits:   { cpu: 500m, memory: 512Mi }
